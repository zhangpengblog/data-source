# 个人投资理财看板

只读看板。**底表托管在 Gitee，应用发布在 WorkBuddy 沙箱**，服务端自己抓公开行情、算指标。

**在线地址：https://finance-dashboard-83938.app.workbuddy.host/**

> 服务端是一个单端口 Python 服务（`_dep/app.py`），只做两件事：
> **① 路由白名单** —— 只放行前端与产出 JSON；底表 CSV、`fetch_data.py`、`app.py` 一律 404
> （不用静态目录服务，避免把整个目录当 webroot 泄露底表）。
> **② 懒刷新** —— 数据超过 TTL（3 小时）就在**后台线程**重跑抓取，**不阻塞请求**，
> 也不依赖常驻定时器（沙箱休眠/重启会让定时器静默停摆）。
>
> 页面右上角显示**数据新鲜度**：超过 20 小时未刷新会转为橙色「可能已过期」。

> ⚠️ **定位已变更（2026-09-17）**：早期本看板是「零成本、不上云」，现已**发布为线上应用**，
> 该定位不再成立 —— 底表在 Gitee 公开仓库，页面在 WorkBuddy 沙箱。
> 底表与产出都含**持仓明细（份额、成本价、盈亏）**，链接请勿外传。

## 数据刷新流程

刷新有**两条链路**，职责不同：

| | **线上**（发布的应用） | **本地**（`sync.py`） |
|---|---|---|
| 触发 | 有访问且数据超过 TTL（3 小时）→ 后台线程自动 | 手动跑 `python3 sync.py all` |
| 抓取 | 服务端直接跑 `fetch_data.main()` | 取底表 → 抓数 → **校验** → 写回 |
| 校验 | 无三层守卫，靠**重试 + 如实降级** | 有：偏离超阈值**直接拒绝写入** |
| 底表来源 | Gitee 仓库（每次刷新前拉取） | `KANBAN_BASE` 环境变量 |

> ⚠️ **线上链路没有 `sync.py` 的 25% 阈值守卫。** 实测过一次瞬时故障（天天基金 SSL 握手超时）
> 只造成 4.6% 偏离，那个阈值本来也拦不住 —— 真正起作用的是**请求重试**（见「网络健壮性」）。
> 抓不到的数据一律标「暂无数据」并写进 `warnings`，**不编造**。

### 本地链路：三层守卫

刷新遵循「先取旧数据当基线 → 生成新数据 → 对比校验 → 通过才写」的顺序：

| 步骤 | 动作 | 作用 |
|------|------|------|
| 1 | `download` | 取回上一版数据当基线，也是回滚材料 |
| 2 | `fetch` | 跑 `fetch_data.py` 生成新数据 |
| 3 | `validate` | 新旧合理性对比，**不过就拒绝写入** |
| 4 | `push` | 校验通过后打印写入清单 |

校验项：总市值偏离旧值是否超 **25%**、当日盈亏是否超总市值 **15%**、
持仓条数、产出文件是否完整、成本与市值能否对上。

> 宁可这一轮不刷新，也不能把错数据留下。校验不过时数据保持上一版，页面不受影响。

### 历史教训（别再走回头路）

早期版本让定时任务用 MCP（网盘）去取配置。但**网盘连接器不在定时任务可挂载的连接器
白名单里**，那个沙箱永远拿不到工具。模型拿不到工具，就自己重建项目、重写 `index.html`、
把数据算错 —— 这是当时所有故障的总根源。

由此定下两条铁律：

1. **定时任务不要依赖任何拿不到的工具**，只用标准能力（命令行 / 标准库）。
2. **`index.html` 必须不在任何写入路径上** —— 让它结构性地不可能被写坏。

## 运行方式

只依赖 Python 标准库，无需 pip 安装。

### 本地起服务（推荐，与线上行为一致）

```bash
cd 理财看板/_dep
PORT=8920 python3 app.py
# 浏览器打开 http://localhost:8920
```

`_dep/app.py` 会自己设好 Gitee 底表地址 → 拉底表 → 抓数 → 算指标，**和线上跑的是同一套代码**。
端口别用 **8899**（那上面已经有一个静态服务在跑）。

### 本地跑完整流程（带三层守卫）

```bash
cd 理财看板
python3 sync.py all          # 取底表 → 抓数 → 校验 → 打印写入清单
python3 -m http.server 8899  # 静态预览（⚠️ 无路由白名单，会连底表 CSV 一起暴露，仅限本机）
```

分步执行（调试时用）：

```bash
python3 sync.py download    # 只取底表与旧数据
python3 sync.py fetch       # 只抓数
python3 sync.py validate    # 只做合理性校验
python3 sync.py push        # 只打印写入清单
python3 sync.py selftest    # 自检：确认前端文件不在任何写入路径上
```

> ⚠️ `sync.py download` 期望的是 `<base>/assets/<底表>` + `<base>/data/<旧产出>` **两级**结构，
> 而 Gitee 仓库现在是**单目录**（`理财看板/data/`），两者对不上，所以 `download` 目前仍不可用。
> 请只跑 `fetch` / `validate` / `push` —— 底表由 `fetch_data.py` 自己从 Gitee 拉（见下）。

### 网络健壮性

- **请求重试**：`http_get()` 对网络类故障（超时 / SSL 握手 / 连接重置）重试 2 次，退避 0.8s / 1.6s。
  ⚠️ **4xx/5xx 一律不重试** —— 403 / 501 是服务端明确拒绝，重试没有意义、还会加重风控。
  这条来自实测：天天基金曾出现 `_ssl.c:1015: The handshake operation timed out`，
  当场连测 4 次却全部成功 —— 是瞬时抖动，**加一次重试就能挡住**。
- **底表多源**：Gitee 主源 → `raw.giteeusercontent.com` 兜底 → 保留本地副本。
  写入前**先校验再落盘**（必须真 CSV、关键列齐全、至少一行数据），挡住坏上传。
- **K 线多源**：新浪 → 腾讯 → 搜狐。
- 抓不到的字段一律标「暂无数据」并写进 `warnings`，**绝不编造**。

## 指标口径（重要）

- **定投累计份额**：按 `dca_plan.csv` 的频率/金额/起始日，逐期用当日实际净值买入并累加份额，非估算。
- **分红复投**：按历史分红记录（每 10 份派现金额 ÷ 10 = 每份）逐次计算，保守按面值再投。
  用户填报的份额**已含**历史再投，不再叠加，避免重复放大份额。
- **支撑位/压力位**：取近一年价格分位锚点（10/25/50/75/90 分位）+ 关键均线（MA20/60/120）+ 布林带 + 波段高低点，筛选与现价保持 1% 以上缓冲的档位。
- **持仓安全度**：距支撑位缓冲 + 近一年价格分位 + 距压力位空间，归一到 0–100。
- **五维评分卡**：**自建口径**，维度对齐通达信诊断专家（基本面/技术面/量价配合/资金面/信息面），各维子指标归一到 0–100。
  **总分 = 有分的维度等权平均**（缺项不按 0 参与，直接不进入分母）。
  实际可用维度：股票/ETF 为**三维**（基本面 / 技术面 / 量价配合），场外基金为**两维**（基本面 / 技术面）——
  即页面上的雷达图目前只有 3 轴或 2 轴，不是 5 轴。**不等于通达信 App 内闭源原始分**。
- **长期预测（三情景）**：按周复利推演 + 每周定投，**按【周】递推**（周金额 × 52 周/年）。
  ⚠️ 这里的 r 是**总回报**（含分红），不是净值涨幅。
  **三档年化回报由每只基金自身历史推导，不再全站统一**（2026-09-16 改）：
  ```
  中性     = 该基金历史实现年化总回报（累计净值口径，含分红）
  σ        = 年化波动率（日对数收益总体标准差 × √252，同一口径）
  悲观/乐观 = 中性 ∓ σ × √(1/投影年数 + 1/历史年数)
  ```
  两个根号项分别是「投影均值自身的抽样波动」与「历史均值的估计误差」。
  **公式是本看板自定口径，不是统计推断的最优解；样本越短越不可靠**（如 024564 只有 1.1 年）。
  所有中间量（实现年化、σ、样本天数与区间、离散度）都随数据下发，并**标注在页面上**，便于复核。
  样本不足 180 个交易日时**不出预测**（宁可缺，不编造）。实测三档（2026-09-16）：

  | 基金 | 样本 | 实现年化 | σ | 悲观 | 中性 | 乐观 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 020602 | 2.42 年 | +7.14% | 13.86% | −2.11% | **+7.14%** | +16.39% |
  | 021457 | 2.12 年 | +11.70% | 15.08% | +0.97% | **+11.70%** | +22.43% |
  | 024564 | 1.08 年 | +3.39% | 11.91% | −8.28% | **+3.39%** | +15.05% |

  > 改这个口径之前，三档是写死的 **−2% / 6% / 14%**（用户最初提供文件里就是这三个整数，
  > **无注释、无出处、未做任何校准**）。现改为数据驱动；那三个整数的痕迹只留在本节这段说明里。
- **年度分红推演（场外基金 · 未来 30 年）**：按你的定投计划推演**每年可得分红（毛额，红利再投前）**。
  **推演按【周】递推**，与计划里的周定投一致（周金额 × 52 周/年）。
  - **分红率**由公开分红全历史推算：`平均每份派发额 × 年派发频次 ÷ 当前净值`，
    频次用相邻派发日的**中位间隔**换算（次/年 = 365.25 / 中位间隔天数）。
    **为什么不直接取「近 12 个月派发合计」**：新基金上市可能不足 12 个月（如 024564 只有 2 笔），
    取合计会把年化水平严重低估。
  - **两个 r 不能混用**。三情景的 r 是总回报（含分红），而分红型基金除息后净值会掉 ——
    若再拿 r 去推净值，等于把分红算了两遍。因此把 r 拆开：
    `周利率 r_w = (1 + r/12)^(12/52) − 1`，`周分红率 y_w = (1+y)^(1/52) − 1`，
    `净值周增速 g_w = (1 + r_w) / (1 + y_w) − 1`。
    于是 `(1+y_w)(1+g_w) = 1 + r_w`，**总市值按 r_w 逐周复利**，两边自洽、不重复计算分红。
  - **每周的计算顺序**：先涨净值 → 再计当周分红 → 最后买入当周定投（即当期投入当期不产生收益，
    与既有 `project_longterm()` 的 `bal = bal*(1+r/12) + monthly` 同规矩）。
  - **与「三情景长期预测」曲线的关系**：两者**已统一为按周递推 + 同一套年化回报**（都取自
    `derive_scenario_rates()` 的推导结果），因此不再存在口径偏差。
    （在此之前该曲线是早期实现的按月口径，与之有 ≤0.44% 的差异，2026-09-16 已一并对齐。）
  - 金额为**毛额**（再投前的分红）；三只基金当前都是「红利再投」，故份额按分红率自动增长。
  - ⚠️ **本口径等价于「每份分红额随净值同比例增长」** —— 因为 `每份分红额 = 净值 × 分红率`。
    基金实际宣告的是**每份固定金额**（020602 近 9 次为 0.008–0.015 元，近一年稳在 0.011 元），
    所以这是一个**稳态假设，不是事实**。实测隐含的每份年分红 30 年倍数：
    **020602 2.47 倍 / 021457 9.31 倍 / 024564 1.01 倍**（差异这么大的原因是各基金推导出的中性回报不同，
    中性越高、分红率越低 → 隐含净值增速越高 → 每份分红涨得越快）。
    **表中已单列「每份年分红」一列**，逐年可见；若要改成「每份分红额固定」，
    只需把递推里的常量分红率换成 `当期每份分红 / 净值`，总回报恒等式 `(1+q/nav)(1+g)=1+r` 依然成立。
  - 为什么仍选「按股息率推」：红利基金的派息来自指数成分股分红，**股息率是它的核心指标**。
    实测 020602 **每次派发当时**的年化股息率为 6.28 / 4.79 / 3.04 / 3.21 / 3.89 / 3.95 / 3.58 / 4.10 / 3.99%，
    均值 **4.09%**，与模型采用的 4.08% 基本一致 —— 这个分红率不是拍的。
    但也要如实说：**两年样本不足以证明股息率长期恒定**（同期每份金额从 0.015 降到 0.011，
    股息率从 6.3% 降到 4.0%）。所以页面同时给出每份分红额，供自行判断。
  - 假设：定投按计划**持续投满 30 年**；未计申赎费、税费；不做任何择时。**仅为模型推演，不构成投资建议。**

## 界面设计（Apple 流体界面）

按 Apple WWDC 流体交互规范实现，核心是「界面对齐人的思考与运动方式」。

**材质与层级**

| 层级 | 用途 | 实现 |
| --- | --- | --- |
| 底层 | 页面背景 | 三层径向渐变 + 极浅噪点，避免色带 |
| 中层 | 卡片/持仓卡 | `backdrop-filter: saturate(180%) blur(24px)` + 半透明底 |
| 高层 | 顶栏 / 抽屉 | `blur(24-34px)`，透光递减、层级越高越实 |

**弹簧物理参数**（对齐 Apple 官方值）

| 交互 | 阻尼比 | 响应时间 | 应用位置 |
| --- | --- | --- | --- |
| 默认 | 1.0（临界阻尼，无过冲） | 0.4s | 卡片悬停、开关 |
| 手势 | 0.8（欠阻尼，少量弹跳） | 0.3s | 抽屉拖拽、分段滑块 |

统一缓动曲线 `cubic-bezier(.32,.72,0,1)`。

**流体交互实现**（详情抽屉）

- **拖拽 1:1 跟随**手指，尊重抓取偏移
- **动量投射**：`project(v) = (v/1000) × 0.998 / (1 − 0.998)`，用投射终点决定吸附/关闭
- **橡胶边界**：上拉越界时 `(1 − 1/((over/limit)+1)) × limit` 阻尼，非硬截断
- **可随时打断**：新动画从实时位置起算，不清空中间状态
- 关闭方式：下拉手势 / 点遮罩 / 点 ✕ / Esc

**光学排版**

- 正文 17px、字距 `-.022em`（对齐 SF Pro 光学补偿）
- 大数字 34px、字距 `-.026em`，等宽数字 `font-variant-numeric: tabular-nums`（数字跳动不位移）
- 层级字号：34 / 24 / 17 / 15.5 / 13 / 12.5 / 11.5 / 11

**色彩**：使用 Apple System Colors（蓝 #007aff、绿 #34c759、红 #ff3b30 等），中国市场涨跌配色为**红涨绿跌**。

**无障碍适配**

| 媒体查询 | 处理 |
| --- | --- |
| `prefers-reduced-motion: reduce` | 所有动效降至 0.01ms，入场动画直接取消 |
| `prefers-reduced-transparency: reduce` | 毛玻璃退化为不透明纯色，移除 backdrop-filter |
| `prefers-contrast: more` | 提高文字与边框对比度，边框加粗至 1px |
| `prefers-color-scheme: dark` | 完整深色模式，图表跟随重绘 |

另支持 `env(safe-area-inset-*)` 安全区适配（iPhone 刘海/灵动岛）。
